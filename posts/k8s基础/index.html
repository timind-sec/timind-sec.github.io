K8s架构组成

Node

  • 是什么：Kubernetes集群中的一台工作机器（可以是物理机，也可以是云上的虚拟机）。
  • 角色：它负责提供计算资源（CPU、内存、磁盘）。每个Node上必须运行两个核心组件：
    • kubelet：负责管理该节点上的容器和Pod。
    • 容器运行时（如Docker、containerd）：负责真正拉取镜像和运行容器。
  • 包含关系：Node 包含多个 Pod。

Pod

  • 是什么：Kubernetes集群中的一台工作机器（可以是物理机，也可以是云上的虚拟机）。
  • 角色：它负责提供计算资源（CPU、内存、磁盘）。每个Node上必须运行两个核心组件：
    • kubelet：负责管理该节点上的容器和Pod。
    • 容器运行时（如Docker、containerd）：负责真正拉取镜像和运行容器。
  • 包含关系：Node 包含多个 Pod。

Container

  • 是什么：一个轻量级的、可执行的软件包，里面包含了应用代码及其所有依赖（运行时、系统库）。
  • 特性：它是真正运行代码的地方。
  • 包含关系：Container被Pod包含，一个Pod里通常运行一个主要容器（业务应用），有时也会运行辅助容器（如日志收集器、代理Sidecar）。

可以看到K8s的架构相比于单纯的AD域还是更加轻量化的，只使用了一台物理机/虚拟机，就可以在上面跑出内网的效果，以往可能需要多台linux虚拟机或者物理机才能跑出域的效果，现在一个Node节点上就可以跑很多个服务（Pod)，而Pod上又有成熟的业务容器（Container）去跑一下常见的业务比如日志、主业务之类的，非常之轻量化

其中怎么去管理这个Pod分区，就是哪些Node节点管理哪些部分的Pods，就得引用到另外一个概念——namespace

Namespace

Namespace能够更合理的规划K8s集群中的Node与Pod分配关系，如下图所示

环境隔离（最常用）

①在一个集群里同时跑开发、测试、预发布、生产环境：

  • dev（开发）
  • test（测试）
  • prod（生产）

这样不同环境的资源不会相互干扰，测试环境的Pod不会误删生产环境的数据。

② 资源配额（分钱分粮）

云资源是有限的（比如整个集群只有 32核 64G内存）。通过Namespace，可以限制每个团队最多用多少：

  • 开发团队 Namespace：最多用 8核 16G
  • 业务A团队 Namespace：最多用 16核 32G
  • 好处：防止某个团队写了个死循环程序，把整个集群的CPU吃光，拖垮所有人。

③ 权限控制（谁能看谁）

结合Kubernetes的RBAC（权限控制），你可以设置：

  • 张三只能操作 dev 空间。
  • 李四只能操作 prod 空间。
  • 好处：生产环境只有运维大佬能碰，普通开发碰不到，避免误操作。

④ 服务发现的范围

在Kubernetes中，Service（服务）的域名规则是：
<服务名>.<命名空间>.svc.cluster.local

这意味着，不同Namespace里可以存在同名的服务（比如都叫 mysql），互不冲突。

总而言之，Namespace就是用来划分业务的，规定开发用这些pods，而业务用这些pods，使得集群CPU空间能够得到更合理的分配，也避免生产环境受到运维部门以外的人员篡改等等，非常的合理

其他核心组件

API Server

集群入口，会先检查你的身份，然后检查权限，还有一个限流的额外操作，类似防护DDos攻击的那种吧

etcd

相当于Kubernetes的数据库，存放了Pod，Node以及各个Service、ConfigMap服务之类的数据（攻击者常攻击的地方）

Scheduler

用于选择并分配Pod，比方说看看有没有还没有被调度到的Pod；然后还会过滤掉资源不足或者存在污点的Node；当Scheduler觉得Node合适了，就会将其与API Server绑定，然后将未分配到的Pod分配给Node（感觉像某滴平台将那些没人敢接的特惠单子自动分配给某个倒霉蛋司机，开玩笑ber）

Controller Manager

k8s中的控制器，常见的有deployment Controller：保证副本中的Pod数量等于你设定的Pod数量；ReplicaSet Controller：具体干活的；Node Controller：检查Node是否挂掉，自动驱逐Pod
其中上述的API Server、etcd、Scheduler以及Controller Manager都是构成Master主节点的成员

kubelet

  1. 接收API Server下发的Pod创建指令

  2. 调用容器运行时（如Docker/containerd）拉镜像、启动容器

  3. 定期上报Node和Pod的健康状态给API Server

  4. 执行Pod的生命周期管理（启动、停止、重启）

    kube-proxy

维护网络规则，实现Service的负载均衡和访问，会监听Service，若有新Service创建，并会写好IpTables/Vps规则，同时Pod想向外访问Service时，kube-proxy也会作为一个代理，让Pod发出的流量导向Service。

K8s渗透基本流程

渗透路径

渗透路径主要就是先通过Web漏洞（文件上传、命令执行等）拿下一个Pod权限之后，然后本地提权，提权之后还需要搜集容器信息（这个流程非常重要，作个标记），然后搜集到容器信息后尝试容器逃逸，最后控制整个集群然后后渗透，后渗透就是一些持久化的操作了
