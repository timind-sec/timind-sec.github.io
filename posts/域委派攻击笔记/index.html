非约束委派攻击

利用原理

普通域用户先向DC域控请求TGT，DC校验身份后返回TGT，然后域用户再向DC要TGS（针对服务A的访问权限），DC返回TGS，然后该用户拿着TGS跟服务A进行认证，并将TGT委托给服务A；经过TGS相关鉴权之后，服务A就会拿着该域用户委派给他的TGT询问DC要一个TGS去访问服务B，然后他又可以用TGS去访问B，跟前面域用户访问服务A一个道理，但是少了TGT的委派，TGT还是在服务A受伤

在上述过程中，服务A获取了被委派用户的TGT，并将TGT缓存到了自己的lsass进程中。其中非约束委派这个属性一般都是赋予给域控的，需要设置SeEnableDelegation特权

从攻击调度上来看，如果攻击者拿到了一个非约束委派的机器A，那么他如果能够模拟DC委派他去访问某个特定的服务，那么A就可以将DC给他的TGT缓存在自身的lsass进程中，然后A就可以利用这个TGT去访问域内的所有其他服务

约束委派攻击

利用原理

基于非约束委派的不安全性，微软在Windows Server 2003中引入了约束委派的机制，引入S4U，其有两个子协议：Service for User to Self和Service for User to Proxy，这两个协议主要是用来允许服务代表用户向KDC请求票据，s4uself是服务代表自己去请求可转发的Kerberos票据（ST1）；s4u2proxy就是以用户的名义去请求其它服务的ST2，而约束委派就是限制了s4u2proxy的扩展范围，让他不去请求这么多的服务

那么如果服务A上设置了约束委派，并可以通过KDC请求一个用户B身份的ST1，ST1 的目标服务（服务A）必须配置了约束委派，并且委派列表中包含目标服务（CIFS/DC）然后服务A再用这个ST1去发起s4u2proxy请求【**如果用户B被标记为”敏感账户且无法被委派”**，则 S4U2Proxy 会失败】。s4u2proxy可使用服务A的ST1去向KDC请求一个服务B的ST2，这张ST2的身份还是用户B的（伪造的），服务A借用了用户B的”身份证”（ST2），去访问用户B有权限的资源。

大致流程：

user访问serviceA，向DC发起kerberos认证，域控返回user的TGT和ST1票据，user使用ST1票据对serviceA进行访问。如果配置了serviceA到serviceB的约束委派，则serviceA能使用S4U2Proxy协议将用户发给自己的可转发的ST1票据以用户的身份发给DC。域控返回serviceA一个用来访问serviceB的ST2票据,这样serviceA就能以用户的身份对serviceB发起访问

主机账户vs服务账户

续，，，笔者对于主机账户和服务账户有些细节上的不理解，问了下deepseek主要有如下

一、主机账户vs服务账户（计算机账户）的本质区别

维度 主机账户（计算机账户） 服务账户（托管服务账户/普通域用户）
名称格式 以 $ 结尾，如 WEB$、SQL$ 不以 $ 结尾，如 svc_iis、testsql
对象类型 computer 对象 user 对象
创建方式 加域时自动创建 管理员手动在 ADUC 中创建
默认权限 低权限，仅能访问域内基本资源 取决于管理员赋予的权限（可能很高）
用途 代表一台物理/虚拟机器在域中的身份 代表一个应用程序/服务在域中的身份
密码管理 自动轮换（每 30 天），由域控推送 管理员手动设定，通常长期不变
登录方式 只能通过机器账户登录系统（NT AUTHORITY\SYSTEM 或 NETWORK SERVICE） 可以通过用户名/密码交互式登录
是否可配置委派 ✅ 可以（在 AD 中设置） ✅ 可以（前提是拥有 SeEnableDelegationPrivilege 权限）

二、在约束委派攻击中的利用差异

1. 获取凭证的方式不同

凭证获取方式 主机账户（如 WEB$） 服务账户（如 svc_iis）
Kerberoasting ❌ 计算机账户默认没有 SPN（除非手动添加），通常无法通过 Kerberoasting 获取 Hash ✅ 如果服务账户关联了 SPN，就可以通过 Kerberoasting 获取 Hash 并离线破解
内存提取（Mimikatz） ✅ 如果拿到了机器权限，可以提权到 SYSTEM 然后从 LSASS 中提取机器账户的票据/Hash ✅ 如果该服务账户的凭证缓存在内存中，同样可以提取
密码猜解/暴力破解 ❌ 计算机账户密码是 120 位随机字符，无法暴力破解 ✅ 如果服务账户密码较弱，可以暴力破解
Pass-the-Hash ✅ 机器账户的 Hash 可以用于横向移动（如通过 SMB） ✅ 服务账户的 Hash 同样可以用于 PtH

2. 配置委派的权限要求不同

配置操作 主机账户 服务账户
在 AD 中配置约束委派 默认需要域管理员权限 默认需要域管理员权限
是否拥有 SeImpersonatePrivilege ✅ 默认拥有（作为机器账户） ❌ 默认没有（除非手动授予）
能否执行 S4U2Self（协议转换） ✅ 可以（因为拥有 SeImpersonatePrivilege） ⚠️ 取决于是否被授予 SeImpersonatePrivilege 以及 userAccountControl 是否设置 TRUSTED_TO_AUTH_FOR_DELEGATION

可能遇到的问题：

  • ⚠️ 如果 svc_iis 没有配置 TRUSTED_TO_AUTH_FOR_DELEGATION（即未启用协议转换），S4U2Self 会失败，因为 KDC 会拒绝该账户模拟其他用户。

解决办法： 在配置服务账户委派时，需要在 AD 中额外勾选 **”使用任何身份验证协议”**（对应 userAccountControl 属性中的 TRUSTED_TO_AUTH_FOR_DELEGATION 标志）。

四、安全检测角度的差异

检测维度 主机账户攻击 服务账户攻击
异常 Kerberos 请求 可能出现机器账户的异常 TGT 请求 可能出现服务账户的异常 TGT 请求
票据注入痕迹 机器账户的 TGT 被注入到非系统进程 服务账户的 TGT 被注入到非预期进程
横向移动路径 从主机 → 其他主机（如 DC） 从服务 → 其他服务（如 DC）
日志事件 4769（服务票据请求）可能来自非预期机器 4769 可能来自非预期用户或时间

五、总结对比表

对比项 主机账户（计算机账户） 服务账户（托管服务账户）
攻击入口 拿到机器权限（如 WebShell、RCE） Kerberoasting、密码猜解、内存提取
获取凭证难度 中等（需要先拿机器权限） 较低（Kerberoasting 可直接获取 Hash）
凭证有效期 票据有效（10 小时）或密码自动轮换 密码长期不变，容易被持久化
S4U2Self 支持 ✅ 默认支持（有 SeImpersonatePrivilege） ⚠️ 需要额外配置 TRUSTED_TO_AUTH_FOR_DELEGATION
攻击成功率 高（配置即利用） 中（取决于管理员是否启用协议转换）
检测难度 中等（机器账户票据请求可能正常） 较低（服务账户票据请求异常）
横向移动能力 强（可访问多个服务） 取决于委派目标 SPN

六、实战建议

  1. 优先攻击机器账户：如果你已经拿到了一台机器的 SYSTEM 权限，优先检查它是否配置了约束委派。机器账户默认支持 S4U2Self，攻击路径最短。

  2. 服务账户的 Kerberoasting：如果你没有机器权限，但拥有域内普通用户权限，可以通过 Kerberoasting 枚举所有配置了 SPN 的服务账户，然后尝试破解。

  3. **检查 userAccountControl**：在攻击服务账户之前，先用 Get-ADUser 检查该账户是否设置了 TRUSTED_TO_AUTH_FOR_DELEGATION 标志。

    powershell

    如果值包含 0x1000000，表示启用了协议转换，可以正常攻击。

  4. 密码策略：机器账户密码自动轮换，即使抓到 Hash 也可能过期。服务账户密码通常长期不变，更适合持久化控制。

如果你还有疑问，比如”如何判断一个账户是机器账户还是服务账户”，或者”如何修改服务账户的 userAccountControl 使其支持协议转换”，可以继续问我。
